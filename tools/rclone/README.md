# rclone helpers for Drive-backed CFS

Optional wrapper around the rclone CLI. Use it when a CFS backend (`{admin}`, the knowledge layer, storage) is on Google Drive and rclone is the available API client. It does not replace `tools/gdrive/` (the bundled Drive API tool).

`cfs_drive.py` implements the guarded read-modify-write that `refs/admin/safety.md` § Writable mirrors requires. Every subcommand prints one JSON line on success and exits `2` with `REFUSED: …` on stderr when a guard fails. Exit `3` with `CONFLICT: …` means another writer got in the way and the tool left everything as it is: its content reached the file right after our upload (`write`), a `--create` left two same-name objects (all IDs are listed), or `append` ran out of retries against other writers. Treat either as an incomplete operation: re-read, redo the edit (merge twins first), and check the result.

| Command | Does | Refuses when |
|---|---|---|
| `read REMOTE LOCAL --state STATE` | `rclone cat` into `LOCAL`; records ID, size, MD5 and modtime in `STATE` | the name has 0 or 2+ objects; the file changed during the read; the download disagrees with the listing |
| `write LOCAL REMOTE --base STATE [--preimage-dir DIR]` | overwrites an existing file in place (same ID); the replaced body is always kept (in `DIR`, else a temp folder) | the body is empty, not UTF-8, has NUL bytes or lacks a trailing newline (checked **before** upload); 2+ objects; the file changed since `read`; the body is smaller (pass `--allow-shrink` for an intended shrink); after upload, not exactly one object, a new ID, or a size/MD5 mismatch. After a bad upload it rolls back **only its own upload**: one object, the same ID, the modtime of our upload file, and a body equal to our bytes or a prefix of them, re-checked just before the rollback. Anything else is another writer's edit: `CONFLICT`, not rolled back. |
| `write LOCAL REMOTE --expect-md5 MD5` | as above, compare-and-swap on MD5 only | as above |
| `write LOCAL REMOTE --create` | creates a new file (new episodics, todos, per-run logs); re-lists the name after the upload | the name already exists. If a same-name twin appears after our upload (another writer created it at the same time), it is `CONFLICT` (exit 3) with both IDs and never `ok`: read both by ID, merge, trash one with `trash --id` |
| `write … --text` / `--binary` | `--text` runs the text checks on a file without a known suffix (e.g. `scripts/gdrive-mount`); `--binary` skips them | |
| `append FRAGMENT REMOTE [--create] [--retries N] [--settle S]` | appends the lines in `FRAGMENT` to a log (or any text file): API read, then `write --base` of body + fragment, with the upload's modtime set to the millisecond as its identity. If the log changed before our upload, nothing was written: it re-reads and appends again (text that matches ours is never taken as ours). Only after a post-write `CONFLICT` does it check whether our own upload landed: rclone confirmed it and the log now starts with exactly the bytes we uploaded and has grown since; then it is done. After `S` seconds (default 3) it re-reads once more: if the log no longer starts with our bytes, or is exactly our bytes under another writer's modtime (a byte-identical line uploaded over ours), our line was overwritten and it appends again. Up to `N` (default 5) retries; `--create` starts a missing file | the fragment is not clean text ending in a newline; the remote does not end with a newline (possible truncation); the remote got shorter between reads (exit 2); the log is exactly our bytes under a modtime more than 120 s from ours, so identity cannot be judged (exit 2, the lines are probably in the log: check before retrying). Exit 3 (`CONFLICT`): retries ran out against other writers (**the lines are not in the log**), or `--create` left a same-name twin (our lines are in one of the twins) |
| `moveto SRC DST` | renames one object (e.g. `-pending-` → `-complete-`) | `SRC` has 0 or 2+ objects; `DST` exists; afterwards `SRC` remains or `DST` differs in ID, size or MD5 |
| `trash REMOTE [--id ID]` | `rclone deletefile --drive-use-trash`; for a duplicated name, `rclone backend moveid` first renames the chosen ID to `<name>.cfs-trash-<ID>`, so **it sits in the trash under that name** | not a Drive remote; the ID is not at that path; a duplicated name without `--id`; the ID is still listed, or missing from `--drive-trashed-only` |
| `restore REMOTE_DIR --id ID [--name NEW]` | brings one trashed object back into `REMOTE_DIR` under its trashed name minus a `.cfs-trash-<ID>` suffix, or under `NEW`. **Before anything moves**, an API listing must show that name free. `rclone backend untrash` restores *everything* trashed in a folder and ignores filters, so the tool moves the object by ID into an empty `.cfs-restore-<ID>` folder, untrashes there and moves it back by ID. It then lists the temp folder (live and trashed) and, only if empty, **deletes it permanently** (`rmdir --drive-use-trash=false`): a trashed temp folder would come back with any later untrash of the parent. Also renames an object already restored by hand | not a Drive remote; the ID is in neither the folder nor its trash; a folder; `NEW` is not a plain name; **the target name is taken: nothing is moved, the object stays in trash; pass `--name NEW`**; the temp folder exists and is not empty (live or trashed); the name gets taken while restoring (the object is put back in trash); size/MD5 differ afterwards |
| `lsjson REMOTE_DIR` | authoritative folder listing | a name occurs twice |

Limits:
- Drive has no server-side compare-and-swap through rclone. Each write has a window of a few seconds, from its last check until its upload has landed. Another writer's upload that lands in that window is **overwritten, and this tool reports success** (`test_toctou_window_is_a_documented_limit`).
- When `CONFLICT` is actually seen: only by a writer whose post-write listing runs **after** the other upload has landed. If writer A's upload is overwritten by B's after A's post-write check, A has already reported `ok` and B sees its own body: both report `ok` and A's edit is lost silently. `write` cannot catch this. `append` catches it with its settle re-read if B's upload lands within `--settle` seconds of A's check; later than that, it is lost silently too. Keep the window small: read, edit and write in one step.
- Shared logs (several agents appending to one file): a concurrent append in the same few seconds can still be lost. Prefer one log file per run (one writer each); keep `--settle` at its default or longer for shared files, never `0`; after a burst of appends, re-read the log if the lines matter. Three-writer corner case not caught: another writer uploads a byte-identical copy of our line from the old base and a third appends on top before our re-read.
- The same gap exists between the rollback's re-check and the rollback upload.
- Drive trash keeps objects for about 30 days; keep a local backup of anything trashed that may be needed later.
- Google-native Docs/Sheets have no MD5 and are refused.
- The tool never reads rclone's credentials.
